# Rebuild WordPress and WooCommerce

## One-command provisioning

On a fresh Ubuntu VM, supply `infra/cloud-init.yaml` as the VM custom data. It installs Docker and Compose, clones this repository, discovers the VM's public IP through Azure IMDS, and runs the provisioning script. Ports **80** (WordPress) and **8000** (FastAPI) must be allowed in the Azure NSG.

On an existing Ubuntu VM, run:

```bash
cd ~/ai-shopping-agent
SITE_URL=http://<PUBLIC_VM_IP> infra/provision.sh
```

Override the host port when port 80 is already occupied:

```bash
SITE_URL=http://<PUBLIC_VM_IP>:8080 WORDPRESS_PORT=8080 infra/provision.sh
```

The stack pins WordPress `7.1.3` / PHP `8.3`, WP-CLI `2.12.0`, and WooCommerce `11.2.1`. WP-CLI installs and activates WooCommerce; the idempotent importer creates or updates nine simple products with stable SKUs derived from the seed IDs. The script configures TND, creates a dedicated `shop_manager` user and one `read_write` API credential, writes it to the ignored `.env`, fetches the actual Woo product IDs, and rebuilds the Chroma index with `all-MiniLM-L6-v2`.

Official WP-CLI supports plugin installation and activation from the command line: [plugin install](https://developer.wordpress.org/cli/commands/plugin/install/). WooCommerce documents REST credentials and the `/wc-auth/v1/authorize` consent flow in its [authentication guide](https://developer.woocommerce.com/docs/apis/rest-api/authentication). For this single-owner demo bootstrap, `create-api-key.php` uses WooCommerce's own key hash/row format from `WC_Auth` so the fresh secret can be captured once by the local provisioning script; reruns reuse the saved credential instead of minting additional keys.

## Secrets and app startup

Generated MySQL values are stored in `infra/.env` (mode `0600`). The WordPress admin password is in `infra/.secrets/wordpress-admin-password`; the WooCommerce REST credentials are in `.env` and `infra/.secrets/woocommerce-api.json`. These paths are ignored by Git. Keep backups of them if preserving a deployment; they are not recoverable from a clean database rebuild.

The Groq key is intentionally not generated by cloud-init. Add it to the root `.env`, then start the app:

```bash
sudo systemctl enable --now ai-shopping-agent
sudo journalctl -u ai-shopping-agent -f
```

Check the services and endpoints:

```bash
docker compose --env-file infra/.env -f infra/docker-compose.yml ps
curl -fsS http://<PUBLIC_VM_IP>/wp-json/wc/v3/products?per_page=1
curl -fsS http://<PUBLIC_VM_IP>:8000/health
```

The provision script is safe to rerun and preserves its Docker volumes. To reset the WordPress database, you must intentionally remove the volumes (`docker compose ... down -v`) before provisioning again; this deletes products, users, API keys, and orders. The cloud-init path has not yet been exercised by deleting and recreating the current VM. That destructive end-to-end check remains for the final CDC acceptance run.

## Demo boundary

This is a reproducible evaluation/demo deployment, not a production commerce setup. The current app uses HTTP Basic authentication for WooCommerce, so expose it only on a trusted demo network until HTTPS is configured; WooCommerce recommends HTTPS for REST API authentication. For a real public store, terminate TLS and set `SITE_URL` to the HTTPS origin.
